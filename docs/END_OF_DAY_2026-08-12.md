# End-of-day report — 2026-08-12

Board: PZ7020-StarLite (Zynq-7000, Cortex-A9). Branch `main`. Commit `649759a`, committed locally.

## Headline

**PhaseHash v1 + a real `BootSessionRoot` + PhaseIndex, all proven on real silicon in one commit.**
The bare-metal boot splash's `BootSessionRoot` is no longer a zeroed stub — it's a genuine
PhaseHash-computed value on every real boot, and `PhaseFs` now carries an additive
`(state, Kairos-sector, Chronos-bucket)` index wired through every mutating filesystem syscall.

This followed the `escher` branch attempt at a full boot-manifest verification system, which
stalled the board and was fully reverted at your instruction. Tonight's scope was deliberately
narrowed to exactly what you asked for: **PhaseHash + BootSessionRoot + PhaseIndex only — no
boot-manifest/stage1** — implemented, tested, and committed as one unit.

## 1. PhaseHash v1 (`kernel::crypto::phase_hash`)

New `no_std` module: a domain-separated `tuple_hash(domain, parts)` construction over SHA-256
(`GP-PH1` magic + length-prefixed domain + part count + length-prefixed parts), plus PH-C
(content), PH-O (reflection-orbit, invariant under `gphase_core::reflect`), PH-S (chained
per-object state hash), PH-R (root-over-leaves and boot-image-root), and a dedicated
`ph_boot_session_root`. 12 construction-correctness tests — each manually rebuilds the exact
`tuple_hash` pre-image byte-for-byte and checks it against a bare `Sha256::digest`, independent of
the function under test. See [PHASE_HASH_V1.md](PHASE_HASH_V1.md).

The original reference vectors from an earlier session weren't recoverable after the `escher`
revert, so rather than guess at matching lost numbers, correctness was reproven from the
construction itself.

## 2. Real `BootSessionRoot` on bare metal (was: zeroed stub)

`kernel::boot_session::compute_boot_session_root` now calls `ph_boot_session_root` under
`any(feature = "std", feature = "baremetal")` — no more `tagged_hash` fallback, no `[0u8; 32]`
stub path.

Found and fixed a second, deeper bug while wiring this in: `kernel::anom::boot::finalize_boot`
only computed `boot_session_root` inside its `#[cfg(feature = "std")]` branch. On every bare-metal
boot the field silently stayed at its zeroed `Default` — the splash's `[SEALED] BootSessionRoot:`
line was never real on hardware, regardless of which hash function backed it. Moved the
computation into a shared `any(feature = "std", feature = "baremetal")` block so both build types
get the real value.

## 3. PhaseIndex (`kernel::phase_index`)

New additive index over `PhaseFs` inodes, partitioned by `(state, Kairos-sector,
Chronos-bucket)`. `Inode` gained `chronos: u64` / `kairos_sector: u8`, stamped by
`PhaseFs::stamp_phase_time` from the live `StateClock` on every create/mutate.
`PhaseIndexController` (`insert`/`remove`/`relocate`/`query_range`) lives behind a `BTreeMap` in
both `std` and `baremetal` builds (added to `platform.rs`'s re-exports for `baremetal`). Wired into
`FS_MKDIR`/`FS_WRITE_FILE`/`FS_LOCK`/`FS_UNLOCK`/`FS_RM` via a `stamp_and_index` syscall helper.
See [PHASE_INDEX.md](PHASE_INDEX.md).

**Bug caught before hardware:** the first `query_range` looped bucket-by-bucket from
`chronos_start` to `chronos_end` — a wide query (`0..=u64::MAX`) would have taken ~10^18
iterations. It hung `cargo test` rather than the board. Fixed by switching to
`BTreeMap::range(start_key..=end_key)`, which only ever touches populated buckets.
